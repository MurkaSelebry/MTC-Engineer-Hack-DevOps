# Протокол испытаний и соответствие кейсу

Испытания выполнены 4 октября 2026 года на двух выделенных VM. Итоговый снимок исходников, количество тестов и результаты приемки указаны в [машиночитаемой сводке](evidence/summary.json). Финальная приемка и повторный deploy выполнены на runtime-коммите из сводки. Recovery, нагрузка и перезагрузка проверялись на предшествующих рабочих снимках в ходе разработки; их собственные timestamps сохранены в JSON, точный Git SHA для каждого раннего прогона отдельно не фиксировался. Публичные IP заменены в JSON на `VM A` / `VM B`; остальные результаты сохранены. Исходные секреты, kubeconfig и SSH-ключи не входят в материалы.

## Среда и воспроизводимость

| Параметр | VM A | VM B |
| --- | --- | --- |
| ОС / архитектура | Ubuntu 24.04.5 LTS / amd64 | Ubuntu 24.04.5 LTS / amd64 |
| CPU / доступная ОС память | 8 vCPU / 15.62 GiB | 8 vCPU / 15.62 GiB |
| Выделенный диск | 200 GB | 50 GB |
| Использовано при последнем контрольном прогоне | 10.07 GiB | 9.88 GiB |
| Свободно в корневой ФС в этом замере | 183.00 GiB | 37.89 GiB |
| Prometheus targets | 15/15 UP | 15/15 UP |
| Grafana | 9 panels, оба datasource OK | 9 panels, оба datasource OK |

Это два независимых single-node кластера, а не двухузловой HA-кластер. Обе машины изначально предоставлены без Kubernetes; разработка и устранение найденных дефектов выполнялись итеративно. На VM B повторный bootstrap проверен с чистым состоянием kubeadm из отдельного Git-клона bundle; системные пакеты и download cache после предварительного прогона сохранились. Анонимное клонирование с публичного Git-хостинга еще не проверялось; его необходимо проверить после публикации `main`.

Развертывание: `./scripts/bootstrap.sh`, `make deploy`. Проверка: `make lint`, `./scripts/verify.sh --host "$VM_IP"`. Ручное создание Kubernetes-ресурсов для рабочего профиля не требуется. Повторные deploy сохраняют данные и не вызывают `kubeadm reset`; контролируемый сброс использовался только при испытании раннего тестового кластера VM B до появления данных приложения.

Полный lint на Ubuntu включает Python tests, shellcheck, YAML/Python/shell syntax, Kustomize render и Ansible syntax check. На рабочей macOS отсутствовал shellcheck, поэтому его фактический прогон выполнен на обеих Ubuntu VM. Hash-locked Python dependencies установлены на VM B из отдельного окружения. Итоговый прогон: 74/74 теста; статические проверки [A](evidence/vm-a-static-checks.txt), [B](evidence/vm-b-static-checks.txt).

После исправления миграции Grafana на обеих VM дважды выполнен итоговый deploy. Между последними повторами совпали Grafana Pod UID, все PVC UID и публичные сертификаты; проверены совпадение файла пароля с Secret, отсутствие перевода строки, авторизация и здоровье обоих datasource. Это исключает ненужный rollout Grafana при неизменных учетных данных: [A](evidence/vm-a-repeat.json), [B](evidence/vm-b-repeat.json).

## Внешний доступ и расширенный Gateway API

Из независимой macOS-машины проверены `/`, `/v2`, `/v2/` по HTTP и HTTPS на обеих VM: 12 успешных проверок, TLS с настоящим `--cacert`, без `-k`. Проверены закрытые 6443/10250/2379/2380 после перезагрузки: [внешний отчет](evidence/external.json).

Полная приемка выполняет 1000 canary-запросов на каждый кластер; диапазон принятия v2 составляет 5-15% вокруг целевых 10%. Точные количества записаны в JSON каждого прогона. Проверки с чужим hostname и чужим CA завершаются именно ошибкой проверки сертификата curl 60.

Все 9 выражений dashboard отдельно выполнены против живых Prometheus/Loki на VM A: ошибок API нет, каждое вернуло непустые данные ([отчет](evidence/dashboard-queries.json)).

В PromQL исключены admin/readiness/scrape counters Envoy. Перед измерением baseline и результата проверяются реальные timestamps метрики для каждого instance; это не позволяет засчитать старую серию canary за новые тестовые запросы.

## Сбои, сохранность и нагрузка

Команда `python3 scripts/recovery-test.py --allow-disruption --host "$VM_IP"` выполнена отдельно от обычной приемки на обеих VM:

- Pod из постороннего namespace не смог напрямую обратиться к Service приложения: соединение завершилось timeout, разрешенный путь через Gateway вернул HTTP 200.
- Удаленный Pod v1 заменен новым, обе реплики готовы, HTTP/HTTPS-маршруты продолжают работать после восстановления.
- Loki остановлен, созданы 100 запросов с уникальными маркерами, Fluentd перезапущен во время недоступности хранилища. После восстановления найдены все 100 access и 100 error-записей. Буфер находился на диске; восстановление Loki выполняется в `finally` с ограниченными повторами.

Отчеты восстановления: [A](evidence/vm-a-recovery.json), [B](evidence/vm-b-recovery.json).

Обе VM перезагружены. После запуска сервисов снова прошла полная приемка. Совпали PVC UID и SHA256 публичных CA/leaf-сертификатов; найдены старые stdout/stderr UUID и точное историческое значение счетчика Prometheus за время до перезагрузки: [A](evidence/vm-a-persistence.json), [B](evidence/vm-b-persistence.json). Это подтверждает сохранение данных, а не только повторное создание Pod.

Короткая нагрузка: 1000 запросов, concurrency 10, на каждом узле получено 1000 точных v1-ответов, ошибок и неотправленных запросов 0. VM A: p95 9.54 ms, 1714 запросов/с; VM B: p95 9.64 ms, 1687 запросов/с ([JSON](evidence/vm-b-load-smoke.json)). Генератор выполнялся на самой VM через ее публичный IP; это короткий функциональный smoke, не независимый benchmark мощности сети или production SLO. [Отчет A](evidence/vm-a-load-smoke.json).

## Найденные и устраненные дефекты

Испытания выявили конкуренцию старого Podman CNI с Calico, конфликт повторного server-side apply с дополненными оператором полями, отличие exit status OpenSSL на Ubuntu, смешение служебных HTTP counters и лишний перевод строки в начальном пароле Grafana. Исправления включены в автоматизацию и acceptance checks. Для существующего Grafana PVC пароль согласуется через API, файл и Secret; потребители Secret перезапускаются при смене учетных данных.

## Границы подтвержденного результата

Один узел и local PV не дают HA или защиты от потери VM. Емкость PV не является квотой; 24h retention и буфер 512 MiB рассчитаны на демонстрационный поток, не на произвольную длительную нагрузку. Не проверены реальное истечение 24h retention, потеря диска, multi-node failover и backup restore. TLS leaf обновляется при deploy, но планировщик и публичный CA не настроены. Alerts вычисляются в Prometheus; внешняя доставка уведомлений отсутствует.
